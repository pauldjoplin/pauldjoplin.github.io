Overview

Enhancement Two focuses on the algorithms and data structures category of the capstone. For this enhancement, I consolidated the original Pricing page and Project Starter into a more structured Project Builder. The updated builder helps potential clients understand what type of website package, support option, or add-on may best fit their needs.

The enhancement focuses on the logic behind the user flow, including how package options are grouped, how selections affect later choices, and how the builder produces a useful recommendation path for the user.

Justification and Improvement

The enhanced builder uses structured service and package data to represent website options, featured bundles, maintenance choices, local visibility support, and other project-related features. These structured objects allow the application to organize information more clearly than if every choice were hardcoded into the interface.

This improvement showcases skills in algorithms and data structures because the system does more than display static content. It processes data, evaluates conditions, organizes related options, and produces user-facing output based on selected criteria.

This improvement made the builder easier to maintain and expand. Instead of relying on repeated frontend code, the enhanced version separates service data from presentation logic and uses decision logic to process that data.

Technical Implementation Details

The enhanced Project Builder uses structured data collections to organize the available website packages, service bundles, maintenance options, local visibility support, and recommendation paths. Instead of treating each option as separate hardcoded page content, the builder organizes related options into arrays and objects that can be processed by the application logic.

Service packages can be represented as objects with fields such as name, category, description, features, priceRange, estimatedEffort, and recommendedFor. Groups of related packages can then be stored in arrays. This allows the builder to loop through available options, filter choices based on user selections, and display grouped recommendations without repeating the same interface code for every possible result. 

packages = [
  {
    name: "Seedling Website",
    category: "static",
    features: ["one-page website", "basic contact path", "mobile-friendly layout"],
    recommendedFor: ["simple presence", "small business", "starter site"],
    weight: 1
  },
  {
    name: "Rooted Website",
    category: "standard",
    features: ["multi-section structure", "stronger service presentation", "contact support"],
    recommendedFor: ["growing business", "service provider"],
    weight: 2
  }
]

The recommendation logic evaluates user selections and maps those selections to service categories. For example, if a user selects that they need a simple online presence, the builder can prioritize static or starter website options. If the user selects request forms, booking needs, or interactive features, the builder can guide them toward more advanced service paths. 

Start Project Builder
Ask user what type of help they need
Store selection in builder state
Compare selection against package categories and recommendation tags
Increase score or priority for matching service paths
Group matching results into recommended package, optional add-ons, and maintenance options
Display a clear summary that nontechnical users can understand

This approach improved efficiency because the user no longer has to move between separate pricing and project-starter pages. The original flow required more steps and created a disconnected experience. The enhanced flow reduced the process from roughly ten steps to five by grouping related decisions together and showing choices that are relevant to the selected path.

The main trade-off was balancing flexibility with simplicity. A fully detailed decision tree could account for many more edge cases, but it would also become harder for users to complete and harder for me to maintain. I chose grouped service paths, weighted recommendations, and “Not Sure / Discuss” options so the builder could remain useful without becoming overwhelming or too rigid.

Reflection

While completing this enhancement, I learned that algorithmic improvements do not always need to make a system more complicated from the user’s perspective. In this case, the better solution was to make the user experience simpler while making the underlying logic more organized.

The original pricing and project-starter experience required users to move through more disconnected information. By consolidating the flow and using structured data, filtering, grouping, and conditional recommendation logic, I reduced the number of major steps from roughly ten to five. This made the builder easier for users to complete while also making the code easier to maintain.

One challenge I faced was deciding how much logic belonged in the Project Builder. A pricing and recommendation tool can easily become too complex if it tries to account for every possible user situation. To address this, I used grouped service categories and weighted recommendation paths instead of building an overly rigid decision tree.

Overall, this enhancement strengthened my understanding of how algorithms and data structures apply to real software products. The Project Builder uses structured data and conditional logic to support practical decision-making, and the improved design makes the website more maintainable and professional.
