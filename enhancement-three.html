Overview

Enhancement Three focuses on the database category of the capstone. For this enhancement, I expanded the Project Builder by creating a database-backed structure that stores service and pricing data used by the builder.

The original version relied on frontend content and static service information. The enhanced version connects Project Builder pricing and service data to a backend database system so that important business information can be stored, retrieved, and maintained outside of the frontend page code.

MongoDB Backend API Service Data Environment Configuration Privacy

Justification and Improvement

The database-backed Project Builder improves the artifact by making service information easier to maintain. If Lucid Grove Studio changes its packages, adjusts maintenance options, adds new service categories, or updates local visibility support, the data can be updated in the backend instead of requiring large frontend code changes.

This supports better scalability because the website can grow without forcing every content or pricing update to be handled directly inside the page layout. The database is used for a specific purpose within the application: storing business-side Project Builder data while avoiding unnecessary storage of sensitive customer inquiry information.

A key improvement was separation of concerns. The database stores the pricing and service content, the backend API retrieves and serves that content, and the frontend Project Builder presents it to the user. This makes the application easier to test, maintain, and expand.

Technical Implementation Details

The database enhancement uses backend-supported service and pricing data for the Project Builder. The purpose of the database is to store non-sensitive business information such as website packages, service bundles, maintenance options, local visibility support, pricing ranges, descriptions, and category information.

A simplified schema for the service data can be described as: 

serviceItem = {
  id: unique identifier,
  name: service or package name,
  category: website, maintenance, local visibility, add-on, or support,
  description: short explanation shown to the user,
  features: list of included features,
  priceRange: low and high estimated range,
  recommendedFor: list of user needs or project types,
  weight: value used by the builder recommendation logic,
  active: true or false
}

This structure allows the Project Builder to retrieve service data from the backend instead of relying only on hardcoded frontend content. The frontend does not need to know how the data is stored internally. It only needs to request pricing and service information from the API endpoint and render the returned data in the builder interface.

A simplified retrieval flow is: 

Frontend loads Project Builder
Frontend sends request to backend pricing endpoint
Backend connects to the database using environment configuration
Backend retrieves active service and pricing records
Backend returns structured JSON data to the frontend
Frontend validates the returned data
Frontend displays packages, bundles, and recommendations to the user

A simplified update flow is: 

Service or pricing information changes
Backend database record is updated
API returns the updated service data on the next request
Frontend displays the new information without requiring major page-code changes

This design improves maintainability because service updates can be handled through the backend data source instead of editing repeated frontend content. It also improves scalability because new service categories or pricing options can be added as records rather than rebuilding the entire Project Builder structure.

Reflection

While completing this enhancement, I learned about the importance of separating data from the frontend interface. In the original version, pricing and service information were more tightly connected to the page code. That approach can work for a small static site, but it becomes harder to manage as the website grows.

A challenge that I faced was managing the overlap between Enhancement Two and Enhancement Three. Both enhancements involve the same Project Builder feature, but they demonstrate different technical skills. Enhancement Two focuses on how the builder processes user selections, organizes service options, and produces recommendations. Enhancement Three focuses on how the service and pricing data is stored, retrieved, and maintained through the database and backend API.

Another challenge was deciding what data should be stored. Since Lucid Grove Studio is meant to avoid unnecessary data collection, I did not want the database enhancement to depend on storing customer inquiries or sensitive user information. Instead, I focused on database-backed service and pricing content.

I also learned the importance of safe configuration practices. A database-backed application requires connection strings, environment variables, and deployment configuration, but those values should not be exposed in a public repository or milestone submission. To support safer development, the submitted files include an example environment file rather than real secrets.

Overall, this enhancement improved the artifact by making the Project Builder more scalable, maintainable, and production-ready. The database-backed structure allows Lucid Grove Studio to manage pricing and service information more cleanly while supporting the larger goal of building a professional, privacy-conscious website.
